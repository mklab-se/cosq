# Cosq 1.0 — Design Specification

**Date:** 2026-07-07
**Status:** Approved design, pending implementation plan
**Target:** cosq 1.0.0 (from 0.9.1). No backward compatibility required.
**Scope decided with Kristofer:** A+B (foundation + shell), C (ask + schema intelligence), D+E (semantic search + query doctor), refreshed `cosq ai skill`. **No MCP server** — the emitted agent skill is the agent-integration story. cosq stays **read-only**.

## 1. Motivation

cosq 0.9 is a solid read-only Cosmos DB query CLI with an excellent stored-query
engine and early NL→SQL generation. But it is blind to everything Cosmos shipped
in 2024–26 (vector search, full-text search, hybrid RRF — all GA), does a
sequential full cross-partition fan-out for every query, re-shells to `az` per
command, supports one account, has no interactive shell, and pins the data-plane
wire version to 2018. Meanwhile ailloy 1.0 gives cosq embeddings, structured
output, and an eval judge. The 1.0 thesis: **from "run SQL from the terminal" to
"talk to your data" — while staying a lean, pipeable, read-only CLI.**

## 2. Current-state facts (July 2026, researched)

- **Data plane REST**: query is `POST .../docs` with `Content-Type:
  application/query+json`; documented `x-ms-version` caps at `2018-12-31`.
  Vector/FTS/hybrid are *query-language* features (through the same endpoint);
  an implementation spike verifies them over REST and finds the newest working
  `x-ms-version`.
- **Search GA**: `VectorDistance()`, `FullTextContains/All/Any`,
  `FullTextScore()`, `ORDER BY RANK`, `RRF(...)` (with optional weights) — GA.
  Fuzzy search GA (Ignite 2025). Vector index types flat/quantizedFlat/diskANN
  GA; vector & FTS policies are container metadata.
- **Auth**: Entra data-plane RBAC is the recommendation (built-in Data
  Reader/Contributor roles); key auth discouraged (`disableLocalAuth`). cosq is
  already AAD-only via az — correct posture, keep it.
- **Metrics**: `x-ms-request-charge` (RU), `x-ms-documentdb-populatequerymetrics`,
  index metrics via `populateIndexMetrics` — all GA.
- **Ops**: hierarchical partition keys GA; GSI preview; integrated cache GA;
  change feed all-versions-and-deletes GA. (Not in 1.0 scope except awareness.)
- **Emulator**: vNext Linux emulator (`mcr.microsoft.com/cosmosdb/linux/azure-cosmos-emulator:vnext-latest`),
  NoSQL + gateway only — the local test option.

## 3. Architecture decision

**Evolve the hand-rolled REST client** (approved): full control, no
preview-crate churn. Parallel fan-out, pk-scoping, metrics headers added to the
existing `cosq-client`. Token caching stays az-based (cache the token, not the
credential). The `azure_data_cosmos` SDK was considered and rejected (0.x
churn, hides fan-out control, heavy tree).

## 4. Foundation (batch A)

### Query engine
- **Parallel fan-out**: cross-partition queries execute per partition-key-range
  concurrently (bounded, default 8) instead of sequentially. RU summed; `-v`
  shows per-range breakdown.
- **Partition scoping**: when the WHERE clause pins the container's partition
  key to a literal or supplied parameter (light SQL scan + container metadata),
  send a single-partition query (`x-ms-documentdb-partitionkey`) with no
  fan-out. Explicit `--pk <value>` forces scoping.
- **New flags**: `--first N` (stop after N rows), `--max-items N` (page size).
- **Wire version spike** (first implementation task): verify
  VectorDistance/FullTextScore/ORDER BY RANK/RRF through REST against a live
  container; adopt the newest `x-ms-version` that works; record findings in
  code comments on the constant.

### Auth & profiles
- **Token cache**: `~/.cache/cosq/tokens.json` (0600), per resource, expiry
  checked with 5-min skew; az invoked only on miss/stale. Same trust model as
  az's own token store.
- **Profiles**: `~/.config/cosq/config.yaml` becomes
  `profiles: {<name>: {subscription, account, endpoint, default db/container}}`
  plus `default_profile`. Selection: `--profile` > `COSQ_PROFILE` > default.
  `cosq init` adds/updates a profile; existing commands are profile-aware.
  Migration: none needed (no backward compatibility) — old config users re-run
  `cosq init`.

### Housekeeping
- `cosq databases` and `cosq containers [--db]` listing commands.
- `serde_yaml` → `serde_yaml_ng`; `colored` 3.x; delete dead
  `ClientError::OpenAI`/`LocalAgent` variants.
- Fix README `cosq ai init` → `ai config/enable`; fix positional filter
  examples in `doc/ai-reference.md`.
- cosq remains read-only: no writes, upserts, deletes, or DDL.

## 5. The shell (batch B)

`cosq shell` — persistent REPL on **reedline**. Prompt shows context:
`cosq (profile) db/container » `.

- **Input modes**: raw Cosmos SQL (multi-line; executes on `;` or closed
  statement + empty line); `? <question>` = ask-mode with conversation memory;
  `:` meta-commands.
- **Meta-commands**: `:profile <p>`, `:db <d>`, `:container <c>`,
  `:format json|json-compact|table|csv`, `:queries`, `:run <name>`, `:schema`,
  `:search <text>`, `:explain`, `:help`, `:quit`.
- **Completion**: meta-commands, db/container names (cached listings),
  stored-query names, and **document field paths** inside SQL from the schema
  card (`c.` → `c.customerId`, …).
- **History**: `~/.cosq/history`, Ctrl-R search.
- Output identical to one-shot commands (results stdout, RU/status stderr) so
  behavior is learnable once.
- The shell holds the cached token and schema cards in memory; one-shot
  commands remain fully supported and script-friendly.

## 6. Schema intelligence & ask (batch C)

### Schema cards
- `cosq schema [container] [--refresh]` builds/prints a per-container card:
  field paths + types + nullability, example values, low-cardinality value
  sets, partition key, vector policy (path/dims/distance), full-text policy,
  and inferred cross-container relationships ("`c.customerId` →
  `customers.id`", from name/value overlap in samples).
- Built from sampled documents (`SELECT TOP 3 * FROM c` + targeted follow-ups),
  distilled by ailloy into YAML; **cached** at
  `~/.cosq/schema/<profile>/<db>/<container>.yaml`; TTL 7 days (configurable);
  project-local `./.cosq/schema/` overrides for teams. Cards are plain
  reviewable files.
- Cards feed every AI prompt (ask, generate, search model-matching, doctor) —
  replacing 0.9's per-invocation sampling.

### `cosq ask`
- `cosq ask "<question>"`: load card (build on first use) → ailloy with
  **structured output** (`json_schema`: `{sql, params, multi_step?, explanation,
  confidence}`) → execute through the normal engine → print result set
  (chosen format, stdout), the executed SQL + one-line explanation (stderr).
- Flags: `--save <name>` (persist as stored query), `--sql-only`, `--yes`
  (skip the confirmation shown when confidence < threshold or the query is an
  unscoped fan-out), `--db/--container/--profile` as elsewhere.
- Multi-container questions may produce multi-step stored queries (existing
  pipeline executor); relationship hints from cards guide step design.
- **Conversation memory** (shell `?` mode): last N exchanges (question, SQL,
  result shape — never full result data) included in the prompt for
  refinements.
- `cosq queries generate` refactors onto the same module (cards + structured
  output); its bespoke sampling and parse-retry loop are deleted.

## 7. Semantic search & query doctor (batches D+E)

### `cosq search`
- `cosq search "<text>" [-c container] [--mode vector|text|hybrid] [--top N]
  [--show-sql]` and shell `:search`.
- Detection from the container's policies (cached on the card):
  - vector policy only → embed query text via **ailloy embeddings**, run
    `SELECT TOP N ... ORDER BY VectorDistance(c.<path>, @qv)`;
  - FTS policy only → `ORDER BY RANK FullTextScore(c.<path>, <terms>)`;
  - both → `ORDER BY RANK RRF(VectorDistance(...), FullTextScore(...))`;
  - neither → degrade to `CONTAINS` keyword query with an explanatory note.
- **Embedding model matching**: pick the configured ailloy embed node whose
  dimensionality matches the vector policy; confirm interactively once; store
  the mapping on the schema card. Mismatch → actionable error.
- No local vector store, no client-side indexing — Cosmos executes the search.

### `cosq explain`
- `cosq explain "<sql>"` (or `:explain` = last shell query): re-run with
  `x-ms-documentdb-populatequerymetrics` + `populateIndexMetrics`, decode both.
- Output: total + per-partition RU, retrieved vs output document counts,
  index utilization (used paths, **recommended paths** incl. composite
  indexes), scan indicators.
- With AI on: a diagnosis in plain language + the concrete indexing-policy
  JSON snippet + whether pk-scoping or `--first` would help. AI off: decoded
  metrics, well formatted. Read-only — prints fixes, never applies them.

## 8. Agent skill, docs, testing, release

- **`cosq ai skill --emit`** regenerated for the 1.0 surface (ask, search,
  schema, shell, explain, profiles, `-q`/JSON piping contract). This is the
  agent-integration story (explicitly instead of an MCP server).
  `doc/ai-reference.md` rewritten alongside.
- **Tests**: wiremock suite for cosq-client (parallel fan-out, pk-scoping,
  continuation, metrics headers, token cache, error mapping); unit tests for
  SQL pk-detection, card parsing, ask/search prompt+schema construction;
  live-verification repo skill (`test-live-experience`) against Kristofer's
  Cosmos account — including `ailloy eval` judging ask-mode answers; vNext
  emulator documented for local runs.
- **Docs**: README/CHANGELOG/CLAUDE.md rewritten at the end.
- **Release**: single 1.0.0 release when the live test passes (internal
  milestones: foundation → shell → AI → search/doctor).

## 9. Out of scope for 1.0

Writes/upserts/deletes and DDL; change feed; MCP server; GSI/integrated-cache
management; Fabric mirroring; local embedding of non-vectorized containers
(the app or a rigg-managed pipeline owns embedding ingestion).

## 10. Open items to verify during implementation

- Newest `x-ms-version` accepted for query POSTs, and whether
  VectorDistance/RRF need a newer value than `2018-12-31` (spike, task #1).
- Exact response envelope for index metrics (base64 field name) on the chosen
  wire version.
- reedline completion API fit for context-dependent SQL field completion.
- Whether `@step.field` dotted parameter names (0.9 quirk) should be renamed
  to safe identifiers during the generate refactor (leaning yes).
